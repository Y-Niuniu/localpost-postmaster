# 自动派发启用验收方案（E）：可执行清单

> 2026-10-02 · 依据 `docs/live-acceptance.md`（E 的 5 项）与 `docs/integration.md`（启用门槛）
> 状态：**方案（未执行）**。生产派发保持 `disabled`。

## 0. 先说结论：E 现在**跑不了**，缺的不是验收而是实现

`localpost/dsh-adapter.mjs` 的注释写得很明确：

> A host integration must provide and verify the focus and acceptance contracts before the receiver
> can dispatch automatically. **No such integration is shipped here.**

适配器的启用条件是四个能力全部为真：

| 能力 | 当前来源 | 现状 |
|---|---|---|
| `wholeTurn`（整轮之后投递） | `runtimeVersion === '0.2.0-rc.2'` | ✅ 运行中的 harness 就是 rc.2 → **为真** |
| `sourceIsRelay` | 代码内固定 | ✅ 为真 |
| `trustedFocus`（可信焦点） | 需要 `focusProvider.trusted + capture() + verifyBinding()` | ❌ **没有实现** |
| `dispatchIdempotent`（持久+幂等受理） | 需要 `acceptance.durable + idempotent + acceptOnce()` | ❌ **没有实现** |

所以：**E 的 5 项验收在补齐这两个提供者之前无法进行**（没有派发路径可测）。

## 1. 焦点问题的实测结论 + 一个替代设计建议

**实测**：在 DSH 宿主侧搜索 `activeSessionId` / `visibleSession` / `focusedSession` / `sessionFocus`
**全部为空**；`currentSessionId` 只出现在**客户端**代码里
（`dsh-client-ui-conversation/lib/client.js`、`dsh-client-ui-subagent/lib/client.js`）。

**含义**：DSH 宿主插件**拿不到"用户当前正在看哪个会话"**。而 codex 的适配器契约恰恰要求一个
"可信焦点提供者"——这是照搬 Codex 桌面（必须猜"当前可见聊天"）的思路。

**建议的替代设计（更安全，且绕开缺失的 API）：显式指定会话绑定，不做焦点猜测**

- 不做"投递到用户当前看的会话"，而是**一次性指定**"信箱会话"（例如某个专门用来收信的 dsh 会话 id）。
- 投递永远只投给**被指定的那个会话**；如果它没在运行 → **保持 pending，fail closed**，绝不退回"最近/最新"。
- 这样 E 的第 1 条从"猜焦点"变成"**证明不会投错**"：你把界面切到别的会话，信**仍然只落在被指定的会话**。
- 对 `trustedFocus` 契约：可由"显式绑定提供者"实现 `capture()`（返回被指定的会话 id）与
  `verifyBinding()`（校验该会话存在且未被替换）。**是否算"可信"需 codex 判定**——这是本方案最关键的一个待批点。

**为什么这比"焦点"更安全**：焦点方案必须**猜**（猜错就把别人的信塞进你正在干活的会话）；显式绑定**不猜**。

## 2. E 的五项验收（按上述设计改写为可执行步骤）

**共同前置**（安全护栏）：

- 使用**隔离测试根**（不碰生产 `C:/AI_ASSIST/.mailbox`）：`work/localpost-e-test/`
- 使用**隔离测试会话**：新建两个会话 A、B（名字建议 `E-test-A` / `E-test-B`），不用于任何真实工作
- 测试信 id 一律 `mcptest-` 前缀；**不进入生产账本**
- 生产 `dispatch` 全程保持 `disabled`；只在测试根内启用
- 每一步记录证据到 `work/localpost-six-gates-evidence/e-acceptance/`
- **任何一步失败 → 立即停止、保持禁用、按 §4 回退**，不"再试一次就好"

| # | 验收项 | 步骤（谁做） | 通过标准 | 证据 |
|---|---|---|---|---|
| 1 | **不投错会话** | ① 把信箱会话指定为 A（dsh 配置）② 我在测试根投一封 `mcptest-1` ③ **你**把 UI 切到 B 并停留 ④ 观察 | 信出现在 **A**；**B 里没有**；receiver 记录 `delivered→A` | A 的 transcript 片段 + B 的 transcript 为空 + receiver 日志 |
| 2 | **等整轮结束** | ① **你**在 A 里起一个明显较长的回合 ② 回合进行中我投 `mcptest-2` ③ 观察投递发生的时间点 | 投递发生在**该回合结束之后**；**未插入**当前回合 | 回合起止时间戳 + 投递时间戳（顺序证明） |
| 3 | **关客户端不丢不重** | ① 我投 `mcptest-3` 之后**你立刻关闭客户端** ② 等待 30s ③ **你**重新打开 ④ 观察 | 关闭期间信保持 pending；重开后**恰好投递一次**（不丢、不重复） | 队列状态文件前后对比 + A 的 transcript 只出现一次 |
| 4 | **幂等** | ① 我制造重复事件（同一封信重复触发 watcher，或重复投递同一 id） ② 观察 | **只产生一次投递**；重复事件被去重 | 投递计数 = 1；队列标记已投 |
| 5 | **丢失确认不二次唤醒** | ① 我模拟"写了但收不到 receipt" ② 观察 ③ 再用显式回执对账 | 标记为**不确定**；**不得**二次唤醒模型；对账后状态收敛 | 状态字段 = 不确定/needs_reconcile；无第二次 followup 调用；对账后转终态 |

**第 2 项的好消息**：DSH rc.2 的 `followup(input)` → `send(input, "next-turn", true)`
语义上就是"整轮之后投递"，所以第 2 项**有原生支持**，需要的是**验证**而不是重写。

## 4. 失败与回退

- 任一项不通过 → **保持 `dispatch=disabled`**，把失败现象、日志、队列状态存档，报告给 codex 与用户。
- **不做**：不通过"设个 capability 标志"绕过（`integration.md` 明令禁止）；
  不静默退化成"投给最近/最新会话"；不在生产根复现。
- 测试根与测试会话在验收结束、证据留档后清理。

## 5. 全部通过之后

1. 由 codex 复核证据 → 给出"可以启用"或"缺什么"的结论。
2. 启用前需**用户明确批准**，并包含一项**书面风险接受**：
   代码/插件仍可被普通进程改写（用户已选 C），因此自动派发**不是**建立在可信边界之上。
3. 启用范围建议**最小化**起步：只对指定会话、只对白名单发件人、只投递不自动回复；
   观察一段时间再谈扩大。
