# 执行边界（第 3 步）：选项说明与实测评估

> 2026-10-02 · 供用户决策 · 技术细节来自 `docs/mcp-registration-plan-v3.md` §二.4 与本轮只读实测。
> **本文件只是方案与评估，不含任何实施动作；实施必须另行批准。**

## 0. 说人话：这一步在解决什么

dsh 启动时会运行 `.mailbox` 里的服务代码。**现在的问题是：谁能改这些文件，谁就能决定 dsh 运行什么代码。**

实测（`icacls`，只读）发现这些主体在 `.mailbox` 上都**有修改权限**：

- Codex 的沙箱用户组 `CodexSandboxUsers`（Modify）
- dsh 沙箱的写 SID `S-1-4-653368769-522399837`（W/D/DC）
- `Authenticated Users`（Modify）
- 两个查不出名字的 SID：`S-1-5-21-1920298460-…-2774449718`、`S-1-5-21-453586369-…-4041696719`（Modify）

**结论：方案里写的「模型不得改服务文件」目前在操作系统这一层并不成立。** 现在真正拦着的只有工具层约束
（各家 agent 的规则、权限确认）和用户的逐项批准——都是"自觉"，不是"锁"。

## 1. 三个选项（成本 / 收益）

### A. 提权部署（把服务代码搬到只有管理员能写的位置）

- **做法**：服务代码放到普通账号写不动的位置（如 `C:\Program Files\...`），部署时由用户点 UAC 提权。
- **收益**：不提权的进程——**包括所有模型、所有沙箱、所有以你身份跑的普通程序**——都改不了它。
- **代价**：
  1. 安装时要你点一次 UAC「是」；以后每次更新这份代码都要再点一次。
  2. **路径变了，import 会断**（见 §2 实测），影响面比"搬四个文件"大。
  3. 只能保护"搬过去的那部分"；没搬的部分照样能改。
- **挡不住**：拿到管理员权限的程序；你自己在 UAC 上点了「是」的任何东西。

### B. 原位收紧 ACL（不搬文件，只改权限）

- **做法**：四份服务文件和 profile 断开继承，去掉沙箱主体与 `Authenticated Users` 的写权限，去掉 Low 标签。
- **收益**：挡住**沙箱**（Codex 沙箱、dsh 沙箱）。比 A 便宜得多，不用搬文件、不动路径。
- **代价/缺口**：**挡不住**和你同一个 Windows token、不进沙箱的进程——那正是"模型直接以你身份跑"的情形之一。
- 另外：改 ACL 属于方案里**不在批准范围内**的动作（核对发现问题只报告，不自动改）。

### C. 书面接受当前风险

- 写进发布记录，明确"当前只靠工具层约束"，靠用户的逐项批准兜底。
- 诚实、零成本，但**等于承认这道锁不存在**。

## 2. 关键实测：A 方案的依赖闭包（codex 要求"不要只搬四个文件就留下断裂 import"）

`.mailbox` 里真实的 import 关系（本轮实测）：

| 模块 | 依赖 |
|---|---|
| `postmaster.mjs`（内核） | `./fs-safe.mjs` |
| `mcp-server.mjs` | `./mailbox.mjs`、`./fs-safe.mjs` |
| `mailbox.mjs` | `./fs-safe.mjs` |
| `gc.mjs` | `./fs-safe.mjs`、`./postmaster.mjs` |
| `receiver.mjs` | `./fs-safe.mjs`、`./postmaster.mjs`、`./mailbox.mjs` |
| `fs-safe.mjs` | 只有 `node:` 内置模块（叶子） |

**要点：`fs-safe.mjs` 是 5 个模块共同的依赖。** 如果把它搬走，内核 `postmaster.mjs`、`gc.mjs`、
`receiver.mjs` 的相对 import 立刻断掉（插件 `lib/index.js` 是用
`file:///C:/AI_ASSIST/.mailbox/postmaster.mjs` 这个绝对 URL 载入内核的）。

因此 A 方案有三种做法，代价完全不同：

1. **只搬 MCP 三件**（`mcp-launch.mjs` + `mcp-server.mjs` + `mailbox.mjs`），
   `fs-safe.mjs` 在两边各留一份。
   - 好处：插件、GC、Postmaster 的任务与启动器都不用动，改动面最小。
   - **代价**：两份 `fs-safe.mjs` 必须永远逐字节一致，否则行为分叉；而 `.mailbox` 那份仍然是可写的
     ——**内核路径的边界并没有真的建立**。
2. **搬全部 6 个模块**，同步改插件内核路径 + GC/Postmaster 启动器（`.ps1`/`.vbs`）+ 插件配置。
   - 好处：内核路径也被保护。
   - **代价**：**插件本身仍在 `tools\` 下、仍可写**——能改插件的人可以把内核路径指回一份可写副本，
     边界被绕过。要真正闭合，插件也得一起搬，连带要动 dsh 的插件装配方式。
3. **只做 MCP 路径**，并**明确声明**内核路径不在此边界内（诚实标注覆盖范围）。

另外还有一个**未解冲突**：方案的验收写着"普通非提权主体不能修改可信 **profile**"。
但 `cordis.patch.yml` 是 dsh 自己的配置，dsh 更新它时需要写权限；
把它锁成只有管理员能写，可能和 dsh 正常更新 profile 冲突。这一点**需要 codex 判定**，
我不能自行决定。

## 3. 还没查清的事

- 两个 `S-1-5-21-…` SID 和 profile 上那个 `S-1-4-529685576-412677121` 写 SID **分别属于谁**，
  方案要求在试点前查明（本轮未查）。
- 用户 token **不保证**能 override 显式拒绝的 ACL；真机操作失败时**不自动改 ACL，只报告**。

## 4. 需要用户拍板的

1. 选 **A / B / C** 哪一条（或"先 B 后 A"这类组合）。
2. 选 A 的话：能接受**装的时候点一次 UAC、以后每次更新再点一次**吗？能的话还需要：
   - 确认采用 §2 里的哪种做法（1 / 2 / 3）；
   - 决定要不要连插件一起搬（那是更大的改动）。
3. 明确一点：**无论选哪个，都不影响现在已经跑通的备份与局长功能**；这一步只是"给代码上锁"。
