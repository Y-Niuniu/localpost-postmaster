## 1. 已批准的更正（八条）

1. **自动派发不是「长期禁用」**，而是**当前保持关闭**；只有 E 验收通过、用户明确批准试点后才可启用。
   纯逻辑实现和假宿主测试不等于启用生产。
2. **50 封容量口径**：只统计**实际进入模型上下文并被宿主确认受理**的不同信件，按 `id + digest` 去重。
   由系统直接处理、未进入模型的 ping/健康检查**不计**；进入模型的 task/result/ping **均计**。
3. **`needs_reconcile` 隔离**：不确定受理必须**固定到原 generation**，并隔离为待核对项；
   不得盲目重投，**也不得无限阻塞整个身份的后续轮换**。切换后新信可进入新 generation；
   不确定信仍只能由**原 generation 或人工核对**收口。
4. **交接文档不能转移所有权**：每封未完成信必须有落盘的 `owner / generation / status`，
   并用版本检查或 CAS 完成**单信所有权转移**；任一时刻不得由新旧会话同时处理同一封信。
5. **机械交接不授予权限**：既有「读信、分析、回复」范围来自**可信策略/用户批准记录**，可在新会话继续；
   改代码、改文件、生产配置等**实施权限不能从交接正文推导**，仍需相应用户授权。
6. **60% 触发器需要宿主遥测**：只有宿主提供稳定 `turn_id` 与可信上下文用量时才启用 ——
   首次独立回合超过 60% 压缩一次；压缩后的下一个独立回合仍超、或回落后再次超，触发轮换；
   压缩失败直接轮换。**缺少任一遥测时关闭该触发器**，仅使用 50 封容量与硬安全余量。
7. **手动与自动必须共用同一个 claim/owner 台账**；模式切换走**冻结、排空、CAS** ——
   不能通过分别加锁而形成两个独立消费者。
8. **周期不是主要触发条件**：不做固定每周强制轮换；可保留**每周健康检查**。

## 2. 当前还缺的实现（四项，属核心工作包）

来源：codex 对自动派发的启用审查。E 五项**本身不够**，需先补齐：

| # | 缺什么 | 要点 |
|---|---|---|
| 1 | **显式绑定提供者** | 实现 `capture / verifyBinding`；把 adapter、route schema、错误码与测试里的 `focusRevision` 改为明确的 **binding 语义**。**不能只把一个 provider 标成 `trusted:true`** |
| 2 | **持久、幂等的受理提供者** | 以 `agent:id` 为 key，写前日志并持久化 `reserved → dispatching → accepted`，崩溃中断进入 `uncertain/needs_reconcile`；跨进程重启仍须去重。DSH rc.2 的 `followup()` **没有**可跨崩溃证明的原子 receipt ⇒ **不要宣称 exactly-once**；可实现并验收的是「正常路径恰好唤醒一次 + 不确定写入绝不盲目重试 = at-most-once wake」 |
| 3 | **到达路由快照的可信生成** | 现在 receiver 只读 `runtime/routes/<mail-id>.json`，而普通信件不会自动获得 route。须由**受控 receiver/host** 在首次发现新信时从**当前显式绑定**原子生成；**发件信封不得自行声明 route** |
| 4 | **人工与自动的单消费者 claim** | 每封信必须有 claim/owner/lease；或在自动 receiver 运行期间让人工入口识别 claim 并拒绝处理。**仅有 receiver 扫描锁不够** |

## 3. 显式绑定契约（替代「可信焦点」）

DSH 宿主侧实测**没有**「当前可见会话」API（`currentSessionId` 只在客户端），
因此契约从 `trustedFocus` 抽象为 **`trustedBinding`**，避免把不存在的「焦点」伪装成已验证。

有效绑定必须满足：

1. 由用户在目标聊天 A 中执行**明确的绑定动作**（「绑定为 LocalPost 收信聊天」）；
   **不能**靠最近会话、mtime、草稿或已加载列表猜测。
2. 持久记录 `hostId + threadId + cwd/project + bindingRevision/generation + createdAt`；
   绑定记录的**来源与所有者可验证**。
3. 每封信**第一次被接收时**复制一份**不可变的到达路由快照**；之后用户切到 B 或重新绑定，
   **只影响新信**，不改变旧信的 A。
4. `verifyBinding()` 校验 A 仍是同一宿主、同一会话、同一 generation；
   A 不在线或身份不匹配 → **保持 pending**。
5. **永不回退**到「最近/最新/当前看起来像」的会话，也不自动创建、恢复或替换会话。

## 4. 验收矩阵

| 维度 | 口径 | 归属 |
|---|---|---|
| 50 封容量 | 只计进入模型上下文并被宿主确认受理的**不同**信件（`id + digest` 去重）；系统处理与健康检查不计 | 轮换核心 |
| `needs_reconcile` 隔离 | 固定原 generation，不盲目重投，不阻塞新 generation 处理新信；仅原 generation 或人工可收口 | 受理提供者 |
| 逐信 owner CAS | 每封未完成信有落盘 owner/generation/status；转移必须逐信 CAS；任一时刻单处理者 | 轮换状态机 |
| 无遥测降级 | 缺 `turn_id` 或可信上下文用量 → **关闭 60% 触发器**，只用 50 封容量与硬安全余量 | 触发决策 |
| 手动/自动单消费者 | 两者共用同一 claim/owner 台账；切换走冻结、排空、CAS | claim 台账 |
| 旧代退役 | `active → frozen → drained → handoff_written → candidate_created → verified → switched → retired`，逐步落盘可恢复 | 轮换状态机 |
| E 验收 | E1–E5 按 `docs/live-acceptance-plan.md` 执行；E6 为人工/自动 claim 互斥 | 真机验收 |
